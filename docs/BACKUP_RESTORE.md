# ClubKeep database backup restore rehearsal

Status: operator-run tooling for the **ClubKeep-only** PostgreSQL database.
This is an independent workstream; it does not create club routes, modify
authentication, migrate production, or alter MenuMinute.

## Why

The existing `clubkeep-release` helper creates a root-protected
`pg_dump --format=custom` before each production migration. Merely producing
a `.dump` file is insufficient proof that data can be recovered. The
`infra/backup/clubkeep-restore-drill.sh` tool verifies archive structure and,
only when explicitly requested, restores it to a newly created disposable
PostgreSQL 17 database.

The separate `backup-restore.yml` GitHub workflow tests this same script
on a **disposable** GitHub-hosted native PG17 cluster. It populates synthetic
users and a club, runs the actual reviewed Prisma migrations, creates a custom
dump, restores it, checks required tables + migration records and synthetic
row counts, removes the scratch DB and rejects malicious file paths, corrupt
archives and symlinks. It has no VPS credentials or remote deployment ability.

## Limitations and safety

- This is a **restore verification tool, not a scheduled backup** or remote
  backup system. A backup produced only before deployments cannot replace
  daily backups with independent offsite retention and monitoring.
- A successful CI rehearsal with synthetic data is not proof that a real
  production dump can be restored. Perform a separately approved restore from
  an actual ClubKeep dump, ideally on an isolated offsite test host.
- **Default mode `--inspect` never creates a database.**
- `--execute` requires root, PostgreSQL 17, and an exact root-owned, mode
  0600/0400 ClubKeep archive under `/var/lib/clubkeep/backups`.
- The script creates `clubkeep_drill_YYYYMMDDHHMMSS_PID`, revokes public
  access to it, restores with `--single-transaction`, validates identity/club
  tables and migration history, and drops the disposable database on exit.
  It never accepts a target database name, so no invocation can restore
  **over the real `clubkeep` database**.
- A restore drill makes a full second copy of protected account and club
  information temporarily. Never run it on a host without sufficient free
  space, operational authorization and approved data handling. A separate
  nonproduction machine is preferred. A scratch database might remain after
  an uncatchable SIGKILL, host crash or I/O failure; investigate and remove
  that specific scratch database manually after checking its identity.
- Never put raw SQL rows or private user data in public CI logs. The script
  prints only count totals, file size and SHA-256 digest.
- Production `clubkeep` and MenuMinute application services are neither
  stopped nor restarted by the tool. It never calls `prisma migrate deploy`.
- Do not create
  `/etc/clubkeep/enable-backup-pruning-after-restore-drill` merely because
  this script passes. That marker also requires a **verified independent
  off-server backup, complete restore rehearsal, and owner approval**.
- The test accepts only archives generated by the operator-controlled
  release process; don't feed it a third-party `pg_dump` because a restore
  runs privileged DDL in a temporary DB.

## Installation after PR review and merge

Install the helper from a **verified pinned Git SHA**. Example from a trusted
local checkout on the target test host:

```bash
git rev-parse HEAD    # Confirm reviewed/merged commit
bash -n infra/backup/clubkeep-restore-drill.sh
sudo install -o root -g root -m 0750 \
  infra/backup/clubkeep-restore-drill.sh \
  /usr/local/sbin/clubkeep-restore-drill
```

Do not add it to the ClubKeep deployment account's `sudoers` rule.
Only an operator with existing administrative access should invoke it.

### Archive inspection (no database changes)

The release helper writes backups under
`/var/lib/clubkeep/backups/clubkeep-YYYYMMDDTHHMMSSZ-<40-char-sha>.dump`.

```bash
sudo find /var/lib/clubkeep/backups -maxdepth 1 -type f \
  -name 'clubkeep-*.dump' -printf '%TY-%Tm-%Td %s %f\n'

# Replace with a real filename shown above:
sudo /usr/local/sbin/clubkeep-restore-drill --inspect \
  /var/lib/clubkeep/backups/clubkeep-YYYYMMDDTHHMMSSZ-<40-char-sha>.dump
```

### Explicit restore rehearsal (prefer a disposable offsite test host)

First transfer the encrypted backup over a private trusted channel to a
test host with its own PostgreSQL 17, keeping the ClubKeep-only directory
layout and root:root 0600 permissions. Record the transfer checksum.

Only with a safe test host and sufficient disk, run:

```bash
sudo /usr/local/sbin/clubkeep-restore-drill --execute \
  /var/lib/clubkeep/backups/clubkeep-YYYYMMDDTHHMMSSZ-<40-char-sha>.dump \
  --port 5432
```

Expected output:

```text
ClubKeep archive verified: clubkeep-...dump
...
Restoring into isolated scratch database (no production DB connections)
Restored row counts (global users / clubs / applied migrations): ...
ClubKeep restore rehearsal PASSED; no application services were stopped
Removing disposable drill database clubkeep_drill_...
```

Check the script's exit status, evidence, elapsed time and scratch-DB
cleanup. Do not share dump files, production emails, or full restored rows
in chat or public GitHub issues.

The next complementary operations task is **independent daily ClubKeep
PostgreSQL backup scheduling + encrypted offsite restic copy**, with
monitoring/alerting and a separate offsite retention/restore policy.
It must be configured using real operator-selected storage and secrets
outside GitHub and the repository.
